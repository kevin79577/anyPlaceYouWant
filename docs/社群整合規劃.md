# 社群整合整體規劃（UI/UX 與技術框架）v0.2

更新日期：2026-11-14。討論初稿。平台規定查證於 2026-11-14，變動很快，動工前必須再對照官方文件確認；標「未證實」的項目來自第三方文章，不可直接當成依據。

## 1. 目標與原則

**目標**：使用者看一個地點時，除了直播，還能看到各社群平台上關於這個地點的近期貼文作為參考，並且可以自己補充。

**原則**（延續 `開發企劃.md` 與 `目的地頁規格.md`）：

1. **不複製內容**：站上只存貼文網址與必要的描述資料，畫面用平台官方的嵌入元件，或連回原平台。不下載、不轉存圖片與影片。
2. **不爬取**：不使用未授權的抓取。小紅書與抖音的使用條款禁止，且有著作權與個資風險。
3. **誠實標示**：每則貼文標示平台、作者、發布日期、收錄方式；拍攝日期不明就寫「拍攝日期未確認」；平台外部搜尋不偽裝成站內結果。
4. **先有內容，再求自動**：先用不需要審核的方式上線，再逐步接上需要審核或付費的自動化管道。

## 2. 各平台能做到什麼（關鍵限制）

| 平台 | 自動搜尋貼文 | 官方嵌入顯示 | 連到原平台搜尋 | 結論 |
| --- | --- | --- | --- | --- |
| **Instagram** | 可以，但很受限：需要商業或創作者帳號、通過 Meta 應用程式審查；每個帳號 7 天內最多查 30 個不同的主題標籤；只能用主題標籤查，不能用地點查 | 可以。2026 年 6 月起 oEmbed 不需要存取權杖，也不需要審查 | 可以 | 自動化只能涵蓋約 30 個重點地點；其餘靠人工與使用者提供連結 |
| **Facebook** | 沒有公開貼文搜尋。只能讀取「指定粉絲專頁」的貼文，需要通過審查（Page Public Content Access） | 可以（同上，oEmbed 免權杖） | 可以 | 適合追蹤各地觀光單位的官方粉專，不適合找一般使用者的貼文 |
| **X** | 可以，要付費（用量計費） | 可以（官方嵌入貼文） | 可以 | **已決定不納入**（2026-11-14）：不做自動收錄、不列入平台篩選與搜尋入口 |
| **Threads** | 可以。官方有關鍵字搜尋 API，需要 `threads_keyword_search` 權限（是否需要審查未證實） | 可以（oEmbed 免權杖） | 可以 | **已決定納入**；嵌入與搜尋入口第 1 階段就做，自動收錄等營運主體確定後再申請 |
| **小紅書** | **沒有**對外的內容搜尋管道。開放平台主要面向品牌方、廣告主與商家（第三方文章說法不一，未證實） | 沒有給外部網站用的官方嵌入 | 可以 | 只能用「連到小紅書搜尋」加「連結卡片」；內容靠人工精選、使用者補充或創作者授權 |
| **抖音** | **沒有**查到對外的影片搜尋管道。開放平台以小程式、帳號經營為主，且通常需要中國大陸的企業主體（未證實） | 未查到給外部網站用的嵌入方式 | 可以 | 同小紅書 |

補充建議：

- **Threads**：已納入，見上表。
- **YouTube**：專案已經在用。它的搜尋可以依關鍵字與發布時間篩選，適合補上「近期旅遊影片」。
- **TikTok（國際版）**：和抖音是不同的平台與規定，日、韓、泰的內容多半在 TikTok。這次沒有查證，若要納入需另外確認。

## 3. 內容怎麼來：四個來源層級

| 層級 | 做法 | 適用平台 | 需要什麼 | 何時做 |
| --- | --- | --- | --- | --- |
| **A. 原平台搜尋入口** | 每個地點提供「在 IG／小紅書／抖音／FB／X 搜尋這個地點」的連結 | 全部 5 個 | 不需要後端 | 第 1 階段 |
| **B. 精選貼文** | 編輯貼上貼文網址，系統用官方嵌入顯示；無法嵌入的平台顯示連結卡片 | 全部 5 個 | 第 1 階段可用靜態資料檔；之後進後台 | 第 1～2 階段 |
| **C. 使用者補充** | 使用者貼上貼文連結或留下文字補充，經審核後顯示 | 全部 5 個 | 後端、審核後台、防濫用 | 第 2 階段 |
| **D. 自動收錄** | 排程用官方 API 依關鍵字或主題標籤查詢 | IG、Threads、YouTube、FB 官方粉專 | 平台審查（需要營運主體的商業驗證）、API 金鑰、排程 | 第 3 階段，**暫緩** |

小紅書與抖音只會有 A、B、C 三層。若之後要更多內容，可行的路是**和創作者合作取得授權**，而不是技術手段。

## 4. UI／UX 規劃

### 4.1 景點詳情頁的結構

```
┌──────────────────────── 景點詳情 ────────────────────────┐
│  ← 返回    世界／日本／京都                         ✕    │
│  京都・祇園花見小路                    ♡ 收藏            │
│  ┌──────┬──────────┬──────┐                              │
│  │ 現場 │ 社群 (12) │ 資訊 │   ← 分頁                    │
│  └──────┴──────────┴──────┘                              │
│                                                          │
│  [現場]  播放器、來源切換、天氣                          │
│  [社群]  平台篩選、時間篩選、貼文牆、補充按鈕            │
│  [資訊]  介紹、座標精度、來源依據                        │
└──────────────────────────────────────────────────────────┘
```

- 目前點地點會直接開串流，這個行為保留；「社群」是同一頁的第二個分頁，分頁上顯示貼文數量。
- 手機版三個分頁改成可左右滑動的區塊，播放器固定在上方。

### 4.2 社群分頁

| 區塊 | 內容 |
| --- | --- |
| 篩選列 | 平台（全部／IG／小紅書／抖音／FB／X／Threads），時間（近 7／30／90 天，預設 30 天） |
| 貼文牆 | 兩種卡片：**嵌入卡**（IG、FB、X、Threads 的官方嵌入）與**連結卡**（小紅書、抖音：平台圖示、作者、編輯摘要、發布日期、「到原平台觀看」） |
| 每張卡片固定資訊 | 平台、作者、發布日期、收錄方式（編輯精選／使用者補充／自動收錄）、「回報問題」 |
| 補充區 | 「我也去過，補充一則」按鈕 |
| 平台搜尋區 | 獨立區塊，標明「前往平台搜尋，結果不在本站」，五個平台各一顆按鈕 |

**載入與效能**：嵌入元件很重，而且會讓平台對使用者設定 cookie。所以先顯示輕量的預覽卡，使用者點了或卡片捲進畫面才載入官方嵌入；一次最多同時載入幾則。

**空狀態**：沿用現有文案原則，例如「近 7 天暫無已收錄分享」，並提供「放寬到 30 天」與平台搜尋入口，不偷偷混入舊貼文。

### 4.3 使用者補充的流程

```
點「補充一則」
  ─▶ 貼上貼文連結（自動辨識平台）或選「只寫文字補充」
  ─▶ 選填：一句話說明（例如「11 月初楓葉約五成」）
  ─▶ 人機驗證 ─▶ 送出
  ─▶ 顯示「已收到，審核後會出現在這裡」
```

- 不需要註冊帳號，降低門檻；用人機驗證與頻率限制防濫用。
- 只接受支援平台的貼文網址，其他網址拒絕。
- 文字補充限制字數，不允許放連結，避免廣告。
- **先上後審**（決定：盡快上架）：通過自動檢查的補充立即顯示，並標示「使用者補充・尚未審核」；編輯事後審核。自動檢查包含：網址必須屬於支援的平台且格式正確、同一則不重複、人機驗證通過、未超過頻率限制、文字補充不含連結與黑名單字詞。
- 被回報達到門檻（例如 2 次）的內容自動隱藏，等待人工處理；後台可一鍵隱藏並封鎖該來源。

### 4.4 其他頁面

- **近期分享頁**（目前是空狀態）：改成跨地點的貼文牆，沿用國家與時間篩選。
- **地圖與清單**：有近期貼文的地點在卡片上顯示貼文數量，讓使用者知道哪裡有內容可看。
- **搜尋**：結果卡片顯示「現場影像」與「社群貼文數」兩種內容標示。

## 5. 技術框架

### 5.1 建議架構

目前是純靜態網站，沒有後端。使用者補充與自動收錄都需要後端。建議**沿用現有前端，加上輕量的無伺服器後端**，不先整個改寫：

```
┌────────────┐      ┌─────────────────────────────┐      ┌──────────────┐
│ 瀏覽器      │ ──▶ │ Cloudflare Pages             │      │ 各平台        │
│ 現有前端    │      │  ├ 靜態網站（dist/）         │      │ oEmbed／API   │
│ + 社群分頁  │ ◀── │  └ Pages Functions（API）    │ ◀──▶ │              │
└────────────┘      │      │                       │      └──────────────┘
                    │      ▼                       │
                    │  D1 資料庫（SQLite）          │
                    │  Cron 排程（自動收錄、檢查）  │
                    │  Turnstile（人機驗證）        │
                    │  Access（後台登入）           │
                    └─────────────────────────────┘
```

| 元件 | 選擇 | 理由 |
| --- | --- | --- |
| 前端 | 現有的原生 HTML／CSS／JS | 已經完成並有測試；社群分頁用同樣的方式加上去 |
| API | Cloudflare Pages Functions | 和靜態網站同一個專案、同一次部署，不用另外維護伺服器 |
| 資料庫 | Cloudflare D1 | 資料量小（數千到數萬筆），內建、免費額度足夠 |
| 排程 | Cron Triggers | 定時收錄與檢查失效連結 |
| 防濫用 | Turnstile 加頻率限制 | 補充與回報不需要帳號 |
| 後台登入 | Cloudflare Access | 不用自己寫登入系統，用信箱白名單保護後台 |

**和原企劃的差異**：`開發企劃.md` 寫的方向是 Next.js 加 TypeScript。建議等到需要伺服器端渲染（SEO）、帳號系統或前端複雜度明顯上升時再遷移；現在先遷移只會重做已經完成的部分。資料庫用 SQL，之後搬到 Postgres 不難。

### 5.2 資料模型（對應 `目的地頁規格.md` 的 SocialItem）

| 資料表 | 主要欄位 |
| --- | --- |
| `social_items` | id、place_id、platform、post_url（唯一）、post_id、author_name、author_url、published_at（UTC）、captured_at（可空）、summary（編輯摘要）、source（editor／user／api）、status（pending／approved／hidden）、embed_ok、checked_at |
| `user_notes` | id、place_id、text、status、created_at、ip_hash（只存雜湊，用於頻率限制） |
| `reports` | id、item_id、type（失效／錯誤地點／不當內容）、created_at、status |
| `ingest_runs` | id、platform、query、started_at、found、added、error |
| `place_queries` | place_id、platform、query（各平台用的關鍵字或主題標籤） |

### 5.3 API（第 2 階段起）

| 方法與路徑 | 用途 |
| --- | --- |
| `GET /api/places/:id/social?platform=&days=` | 取得已核准的貼文，有快取 |
| `POST /api/places/:id/social` | 使用者補充連結或文字，需要人機驗證 |
| `POST /api/reports` | 回報問題，同一則去重 |
| `GET／POST /api/admin/...` | 後台：待審清單、核准、隱藏、編輯摘要（受 Access 保護） |

公開 API 不回傳未核准的內容、金鑰與管理備註。

### 5.4 安全與法遵

- **內容安全政策**：目前只允許 YouTube 與 Open-Meteo。加入嵌入後，要逐一加入各平台的指令碼與框架網域，並重新跑安全標頭下的瀏覽器測試。
- **隱私**：嵌入元件會讓平台取得使用者資訊，所以採用「點了才載入」，並更新隱私權政策。使用者補充只存必要資料，IP 只存雜湊。
- **著作權**：只顯示官方嵌入或連結；編輯摘要自己寫，不貼上原文與原圖。
- **下架**：提供回報與聯絡管道，收到權利人要求立即隱藏。
- **平台條款**：依各平台規定快取、更新與刪除資料；API 金鑰只放在後端。

| 階段 | 內容 | 需要後端 | 粗估 | 完成門檻 |
| --- | --- | --- | --- | --- |
| **1. 入口與精選** | 社群分頁介面、五個平台的搜尋入口、精選貼文（靜態資料檔）、IG／FB／X 嵌入與小紅書／抖音連結卡、近期分享頁改版 | 否 | 1～2 週 | 首批 8 個地點各有 3～5 則精選貼文；安全標頭下測試通過 |
| **2. 補充與審核** | 後端、資料庫、使用者補充、回報、審核後台、失效連結檢查 | 是 | 2～3 週 | 補充到上架的流程走通；濫用防護有效 |
| **3. 自動收錄**（暫緩） | IG 主題標籤、Threads 關鍵字、YouTube、FB 官方粉專 | 是 | 3～4 週，另加平台審查等待 | 等營運主體與商業驗證確定後啟動；YouTube 不需要商業驗證，可以先做 |

粗估是一個小團隊的工作量，不含平台審查等待時間，也不含內容人工整理的時間。

## 7. 成本與限制試算

- **IG**：每個帳號 7 天 30 個主題標籤，等於自動化只能涵蓋約 30 個地點；175 個地點要分批輪替，或只做重點地點。
- **X**：不納入，沒有費用。
- **Cloudflare**：Pages、Functions、D1、Turnstile 在這個規模多半落在免費額度內；流量成長後再評估。
- **人力**：最大的持續成本是**審核**。每則貼文都要有人確認地點正確、內容合適。

## 8. 風險

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| 小紅書、抖音內容量不足 | 使用者期待落差 | 介面誠實標示；主推搜尋入口；鼓勵使用者補充；之後找創作者合作 |
| 平台審查不通過或政策改變 | 自動收錄中斷 | 四個來源層級互相備援，A、B、C 不依賴審查 |
| 貼文被刪除或改為私人 | 出現壞掉的卡片 | 排程定期檢查，失效就隱藏；使用者可回報 |
| 垃圾補充與廣告 | 內容品質下降 | 先審後上、人機驗證、頻率限制、只接受支援平台的網址 |
| 地點對不上 | 貼文其實不是這個地點 | 主題標籤與關鍵字由人工設定；審核時確認；提供「錯誤地點」回報 |

## 9. 決策紀錄（2026-11-14）

| # | 題目 | 決定 | 對規劃的影響 |
| --- | --- | --- | --- |
| 1 | 小紅書、抖音；Threads | 小紅書與抖音維持「搜尋入口＋連結卡片」；加入 Threads | 平台清單：IG、Facebook、Threads、小紅書、抖音 |
| 2 | 使用者補充要不要帳號 | 不用帳號 | 用人機驗證與頻率限制防濫用 |
| 3 | 審核與上架速度 | 盡快上架 | 採先上後審：自動檢查通過就顯示並標示未審核，回報達門檻自動隱藏 |
| 4 | X | 不納入 | 移除 X 的收錄、篩選與入口；沒有 API 費用 |
| 5 | 營運主體與商業驗證 | 先不處理 | 第 1、2 階段不受影響（嵌入免審查）。第 3 階段的 IG、Threads、FB 自動收錄需要 Meta 審查，暫緩 |
| 6 | 技術路線 | 同意 | 沿用現有前端，加 Cloudflare Pages Functions 與 D1；之後再評估 Next.js |

**小紅書與抖音為什麼還有入口和卡片**：「不能搜尋」是指本站無法用程式到這兩個平台裡找貼文。搜尋入口只是一個帶著關鍵字的連結，點了會開啟對方自己的搜尋頁，結果不在本站；連結卡片的內容是編輯或使用者貼上的網址，不是程式抓取，卡片只放連結，不複製圖文。這兩個平台的內容量取決於有多少人提供連結。

**待確認**：小紅書與抖音的網頁版搜尋網址在未登入、手機瀏覽器與 App 內的實際行為（可能要求登入或導向 App），第 1 階段開工時實測。
